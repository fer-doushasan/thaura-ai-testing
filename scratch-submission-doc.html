Qtec Solutions Limited — SQA Engineer Assessment

Application under test: Thaura AI (https://thaura.ai / https://backend.thaura.ai)
Assessment window: 2026-09-14 to 2026-09-15
Companion file: Test Cases / Bug Report / Observations spreadsheet (submitted alongside this document)

1. Executive Summary

Thaura AI is a consumer chat application ("ethical AI companion") with a free tier (5 messages / 5 hours), file upload/analysis, an automatic long-term memory subsystem, an Incognito mode, and a separate OpenAI-compatible paid developer API. This assessment covered functional, session/security, quota, file-handling, memory/incognito, and API testing (Task 01); website technical/functional/performance/security testing (Task 02); and a personal reflection on AI-assisted testing practice (Task 03).

The product behaves correctly and safely across the large majority of tested scenarios. No exploitable security vulnerability was identified within the scope of the security checks performed — this does not constitute a complete security audit. One reproducible frontend defect was found (a React hydration error present on every marketing page). A handful of nuanced observations are documented, most notably around how the automatic memory feature actually triggers, and a wording-precision gap between marketing copy and the legal Data Processing Addendum regarding encryption. A defined, small set of deeper API behaviors remain billing-gated and were deliberately not pursued, with reasoning documented below.

2. Test Environment

  • Application: https://thaura.ai (frontend), https://backend.thaura.ai (API)
  • Test account: a single dedicated QA account ("Qa Test", Free Plan) created for this assessment — not a real third-party account
  • Automation: Playwright (Chromium, headless), Node.js
  • Auxiliary tools: Google Lighthouse (performance/SEO/accessibility/best practices), Apache JMeter (conservative load baseline), Python 3 (openpyxl for reporting, Pillow for evidence redaction)

3. Testing Approach

Testing combined scripted, evidence-generating automation with manual interpretation of results, deliberately favoring a small number of well-designed, information-dense test messages over exhaustive brute-force testing — the free tier's 5-message/5-hour quota made this a hard constraint. Where a test's own automation logic produced a surprising result (e.g. an apparent incognito "leak"), the underlying DOM/network evidence was re-inspected before accepting the result — this caught two automation bugs (a broken incognito-toggle selector, and an over-broad sidebar-text selector) that would otherwise have produced false findings. This distinction — verified finding vs. automation artifact — is preserved throughout this report.

Scenario: Do Incognito-mode messages consume the same free-tier quota?
Actual Result: Yes — remaining decremented identically to a normal message (2→1).
Status: OBSERVATION (not a bug; simply not obvious from UI copy)
Evidence: memory-incognito-test/incognito-verified-results.json.

Test ID: QUOTA-007 — Failed/errored assistant response and quota consumption

Scenario: Does a failed/errored assistant response still consume a free-tier message? Quota was checked before and after a controlled, safe attempt to induce a failure.
Steps: 1) Checked quota (remaining=1). 2) Sent a message requiring a long streamed reply. 3) Reloaded the page ~1.6s later to drop the client connection mid-stream (a safe, realistic scenario — not an abusive technique). 4) Checked backend turn state and quota afterward. 5) Separately, sent a malformed payload directly to the session-authenticated completions endpoint with quota already at 0.
Expected Result: Determine whether a genuine failure consumes a message.
Actual Result: The backend has a resumable-turn architecture — generation completed successfully server-side regardless of the client disconnect, and the UI resumed and displayed the full, correct answer after reload. This was a successful, interrupted response, not a failed one; quota was correctly consumed for a successful turn. The malformed-payload probe returned a clean 400 and did not consume quota (quota stayed at 0). Neither scenario constitutes a genuine assistant-side (generation) failure.
Status: NOT TESTED
Reason: A genuine assistant-side generation failure could not be safely and deliberately reproduced without abusive techniques (e.g., adversarial prompts intended to crash the model, or resource-exhaustion attempts), which were explicitly out of scope.
Limitation: What was verified: client disconnects do not cause failures (backend resumes and bills normally); request-validation errors (400) are not billed. What was not verified: behavior when the assistant's own generation genuinely errors out mid-response.
Evidence: quota-test/failed-response-quota-test.json, malformed-session-request-results.json.

6. Task 03 — AI & Testing Reflection

1. How will AI impact software testing in the next 2–3 years?

The biggest shift won't be "AI replaces testers," it'll be AI collapsing the time between having a test idea and having evidence for it. Right now a lot of QA time goes into the mechanical part — writing the Playwright boilerplate, generating edge-case fixtures, parsing network logs, drafting the bug report — rather than the actual judgment part: deciding what's worth testing and what a given result actually means. Over the next 2–3 years that mechanical layer will keep shrinking; exploratory testing sessions will increasingly look like a tester describing intent in plain language and an AI agent driving the browser/API, capturing evidence, and coming back with a structured first draft of findings — close to how this assessment was actually worked through. What won't go away is the judgment layer: deciding whether a decremented quota counter after a dropped connection is a bug or a resumable-turn feature, deciding whether a long-lived cookie is a real security issue or just a product choice, deciding when a "leak" your own automation flagged is actually a false positive from a bad selector. That discipline — including the discipline of not fabricating a result you didn't actually observe — is exactly where a human tester's value moves to.

2. How have you personally used AI to help with testing?

On this exact assessment: an AI coding agent (Claude Code) was used to write and iterate on the Playwright automation for almost every test area — the OTP/login flow, the 5-message quota exhaustion test, the file-upload matrix, the memory/incognito probes, and the direct API validation batch. It also helped debug a real automation bug mid-session: an "incognito toggle" click was silently failing because it targeted a screen-reader-only span instead of its parent button, and an overly broad .catch() was swallowing the resulting timeout — pulling the actual DOM structure and spotting the mismatch happened faster with the agent driving the diagnosis than manually inspecting minified HTML. It was also used for deterministic test-data generation (PDF/XLSX/PNG fixtures with known embedded markers, so extraction accuracy could be verified exactly), for analyzing raw API/network JSON at volume, and for drafting the structured write-ups from that raw evidence.

3. Which AI tools do you currently use?

Claude Code (Anthropic) was the tool used throughout this assessment — as an agent that writes and runs Playwright/Node scripts, calls APIs directly for validation testing, and turns raw evidence into structured reports. Alongside it, standard non-AI QA tooling was used for the parts that don't need a model in the loop: Lighthouse for performance/SEO/accessibility scoring and JMeter for baseline load testing — listed here for completeness, not counted as "AI tools," since the value they add is deterministic measurement, not reasoning.

4. Which AI testing tool has been most helpful and why?

Claude Code, specifically for the agentic part rather than just code completion. The most helpful pattern wasn't "generate a test script" in isolation — it was the loop of: run a probe, look at the actual response/DOM, notice something inconsistent (like a false-positive "leak" caused by a selector capturing the wrong element, or a chat-quota result that only makes sense once you realize the backend has resumable streaming turns), and revise the next test based on that, all within one continuous session. For an assessment like this one, where a lot of the real findings come from noticing when your own tooling is misleading you, having the same agent write the probe, read the raw output, and flag the discrepancy in one pass was more valuable than any single generated test case.

12. Automation Strategy

Playwright (already demonstrated in this assessment's scripts): auth/OTP flow, session/logout invalidation checks, chat quota exhaustion and reset-window verification, the file upload matrix and extraction-accuracy assertions, navigation/link/redirect checks, metadata/canonical checks, pricing-toggle consistency, and console/network error monitoring as a standing regression check (this would have caught BUG-001 automatically if wired into CI).

API automation (Playwright-API or Postman/Newman): structural/negative/boundary validation — a natural fit given the 14-case validation batch already produced.

JMeter: conservative load/performance baselining on public pages, expanded deliberately and incrementally if real load testing is later authorized.

Lighthouse: performance/SEO/accessibility/best-practices scoring, run per-release against a fixed page set.

Keep manual/hybrid: AI response quality and extraction-accuracy judgment (automation can capture the response; a human should judge correctness); memory semantics (the automatic memory subsystem responds to real usage patterns over time, not a single scripted probe); incognito behavior interpretation (automated leak-detection selectors can produce false positives that need human DOM-level verification, as this assessment demonstrated); and security interpretation/severity classification (a status code is easy to assert in a script; whether a behavior constitutes a real security concern is a judgment call).

This assessment deliberately did not build a full automation framework — the priority was completing manual/hybrid verification of every requirement first. The scripts produced are a reasonable starting point for a future framework, not a finished one.

13. Limitations

  • A mid-session environment reset deleted several evidence files after they were generated during finalization; the underlying structured data (JSON) was recovered verbatim from the session's own tool output and is clearly marked as recovered, but 11 screenshots from those two test runs could not be byte-for-byte restored and are considered lost.
  • Image-embedded-text readability by the assistant in a live chat turn was not independently re-verified this round (budget was prioritized toward memory/incognito/isolation tests).
  • Cross-account file isolation was not tested — scope excludes use of another real person's account.
  • A defined set of deeper API parameter/behavioral tests and rate/concurrency limits remain billing-gated; funding was evaluated and explicitly not recommended.
  • A genuine assistant-side (generation) failure could not be safely reproduced without abusive techniques.
  • This assessment does not constitute a complete security audit — findings are scoped strictly to what was directly observed and verified.

14. Conclusion
